**2026-09-17 (later) — the principle that resolved the aggregation design (user's own, not in the design doc):**

> Every node's maximum must be **static and identical for all students** (`node.points`). Any per-student, dynamically-shrinking quantity (`effectiveMax`) must be kept separate and must **not** feed score computation.

User's reasoning: grades have to be justifiable to a student who objects, so two students cannot be graded against different maxima for the same node. This is the constraint that settles every open aggregation question — record it before the doc does.

It collapses the model to one formula: **every node derives a ratio in [0,1] from its children, then `score = node.points × ratio`.** The aggregation rule only decides how the ratio is derived; scale enters in exactly one place. Consequences worked out (design discussion, **nothing implemented yet — awaiting user's decisions**):
- SUM (`Σ child_score / Σ child_points`) is **provably identical** to a points-weighted average, so `WEIGHTED_AVERAGE` is only a distinct rule if it means the *unweighted* mean of child ratios ("each child counts the same regardless of its test count"). Proposed split: SUM = points-weighted, AVERAGE = equal-weight.
- MIN_CHILD/MAX_CHILD must work on child **ratios**, not raw scores — the user's `MAX(children_points)` version only holds when children have equal points.
- `effectiveMax` stays in `NodeResult` but becomes **non-load-bearing / audit-only** (`node.points × (Σ_assessable child_points / Σ_all child_points)`): it drives neither score nor `validated` (now `score/node.points >= threshold`), and exists to answer "why was I graded on a reduced basis". Do **not** delete it — the transparency case is exactly why the user cares.
- Exclusion must stop being encoded as `effectiveMax == 0`; use `absenceStatus ∈ {IGNORED, ABSENT_IGNORE}`. A non-leaf whose children are all excluded is itself excluded.
- The user's own SUM formula was written inverted (`points / ratio` instead of `points × ratio`).

**Bonus/malus — settled 2026-09-17, documented, not yet implemented.** Decisions, all the user's:
- **Test names are unique within a submission definition** — a deliberate simplification. Anything that would naturally be one test per occurrence (one per trashfile, one per warning) becomes a *single* failing test listing the occurrences in its message. So a malus is the same for 1 trashfile or 10, and the "count failing tests in a category" machinery is **not needed** — an adjustment node is just a leaf. This also kills the need for a `cap` on adjustments.
- Adjustment stored as a **ratio** (fraction of the scale it applies to), never absolute points — absolute would only be meaningful at the root and would need a migration when they generalise to per-level adjustments later. Frontend converts from a fixed point value; a ratio/fixed toggle may come later.
- `GradeReport.adjustmentTotal` is a **separate field**; `finalGrade` never includes adjustments. They combine only at export: `clamp(finalGrade + adjustmentTotal, 0, finalMax)`. Same transparency argument as `effectiveMax`.
- Adjustment nodes **stay in the tree** (excluded from their parent's ratio, like ignored nodes) rather than living in a flat list on the scheme — the user wants per-level application later, and nodes-in-tree makes that a change to *where the deduction lands* rather than a re-model. For v1 position is purely organisational.
- Shape: nullable `GradeAdjustment { kind: BONUS|MALUS, ratio: double }` embeddable on `GradingNode`. MALUS fires on test failure, BONUS on pass; an **absent test never fires either** (which is what makes "no trashfile = no malus" free). No `appliesOn` field — `kind` already carries it.
- "A node whose children are all adjustments" needs **no special case**: adjustment nodes are excluded, so the already-agreed "non-leaf with no non-excluded child is itself excluded" rule covers it.

**FIRST THING NEXT SESSION — `effectiveMax` semantics, raised by the user's own code review on 2026-09-17 and explicitly deferred ("we will talk about that effective max later"):**

`computeGradingNode` computes `effectiveMax = node.points x (assessable child points / all scoring child points)`. That is right for `SUM`/`AVERAGE`, where children are **parts** of the node. It is wrong for `MIN_CHILD`/`MAX_CHILD`, where children are **alternatives**: a MIN node worth 10 with three alternatives worth 5 each, one ignored, still reaches a complete verdict over the two survivors, yet reports `effectiveMax` 6.67. Proposed fix (not implemented, not agreed): for MIN/MAX, `effectiveMax` should be the node's full `points` whenever at least one child survives, `0` when excluded. **Scores are unaffected either way** — MIN/MAX derive their ratio from child ratios and never read points, so this is audit-column semantics, not a grading bug.

Related naming point raised at the same time: `score > effectiveMax` is possible in general (it is asserted on purpose in `anIgnoredChildShrinksEffectiveMaxWithoutDilutingTheScore` — score 10, effectiveMax 5), because scores are rescaled at each node so an excluded child never penalises the student. So `effectiveMax` is **not** an upper bound on score despite its name; suggested rename `assessedMax` if the field is touched.
