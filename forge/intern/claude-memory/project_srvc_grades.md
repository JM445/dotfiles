As of 2026-08-25, ingestion-testing (activity/submission aggregates only, no trace parsing yet) was **done**: 11/11 tests passing across `DataIngestionServiceTest`/`ActivityIngestionTest`/`SubmissionIngestionTest`, using the repo's `TestService`-bypasses-Kafka convention. Real bugs found/fixed then: Flyway migration path, persist-before-setting-fields on new Submission/Job (see [[project_hibernate_persist_ordering_gotcha]]), `@NotFound(action=IGNORE)` on dangling FKs after pruning, and a `group_member` unique constraint.

**2026-08-26 session — trace ingestion mechanism implemented:**

- Found the existing JUnit-XML parsing machinery already in the monorepo (`toolkit/framework/framework-trace`): `Xml.deserialize(xml, Trace.class)` / `Xml.fromFile(path, Trace.class)` (in `framework-core`'s `Xml` util) parses `<testsuites><testsuite><testcase>` XML into `Trace`/`TestCase`/`Failure`/`Error`; `TraceAsTree.fromTrace(trace)` turns the flat `classname`-dotted list into a category tree. Consumed elsewhere by `port-frontend/ActivityService` and `srvc-packager/ResultsUploadService`. `job.traceUrl` is a **raw S3 object key**, not a URL — pass it straight to `s3ObjectService.getObject(S3BucketType.TRACES, job.traceUrl)`, no reformatting (confirmed by tracing it from `ResultsUploadService`'s `putObject(TRACES, uploadUrl, ...)` through `JobResultsUploadedEvent.traceUrl` to `Job.traceUrl` unchanged). Traces are pre-validated (`trace.isValid()`) by `srvc-packager` before upload, so `srvc-grades` doesn't need to re-validate on read.
- Added `DiscoveredTestModel`/`DiscoveredTestRepository` (catalog table: `activityUri`, `assignmentUri`, `classname`, `testKey`, `firstSeenAt`, `lastSeenAt`, `occurrenceCount`) and swapped `TestResultModel`'s duplicated `classname`/`name` strings for a `discoveredTest` FK — the two items left open from the 2026-08-25 design session.
- Key design correction mid-session: `DiscoveredTest`'s natural/unique key is `(assignmentUri, classname, testKey)`, **not** `(activityUri, assignmentUri, classname, testKey)` — URIs on this intranet are globally unique and built by concatenating parent URIs (see [[reference_intranet_uri_convention]]), so `assignmentUri` already implies `activityUri`; adding it to the key would add no real uniqueness. `activityUri` is kept as a plain non-key column purely so activity-wide queries (an `Exam` spans multiple assignments under one activity) don't need to first enumerate every assignment URI. Also renamed the field from `assignmentSlug` to `assignmentUri` — no URI parsing is needed anywhere; `SubmissionDefinitionModel.assignmentUri` already carries the full URI verbatim.
- Design discussion on correlating `TestResult` → student: rejected adding a `Group` entity (would add DB-integrity benefits but no new data, and would force the two currently-decoupled ingestion paths — `onActivityAggregate` writing `GroupMember`, `onSubmissionAggregate` writing `Submission.groupSlug` — to coordinate a find-or-create, a real new failure mode/race for no data gain). Went with query-layer helpers instead: `GroupMemberRepository.groupSlugForLogin(def, login)` → `Optional<String>` (a student is in exactly one group per submission definition — enforced elsewhere, confirmed by the user via a rejected deploy attempt) and `SubmissionRepository.findByDefinitionAndGroup(def, groupSlug)` → `List<SubmissionModel>`.
- User wrote `DataIngestionService.ingestTrace` (called from `ingestJob` only when `job.traceUrl` changes, so retries reparse for free) — upserts `DiscoveredTest` by key, then upserts `TestResultModel` by `(job, discoveredTest)` via new `TestResultRepository.findByJobAndDiscoveredTest`, matching the retry semantics: same `Job.id` + new `traceUrl` must **update** the existing `TestResult` row, not duplicate it, since `DiscoveredTest` resolves to the same row across the retry. Added a matching DB safety net: `idx_test_result_job_discovered_test` unique index on `test_result(job_id, discovered_test_id)`.
- Code review of that `ingestTrace`/`ingestJob` wiring surfaced one real bug (not yet fixed, for next session): `ingestJob` calls `ingestTrace(model, submission)` *before* `jobRepository.persist(model)` for new jobs — `ingestTrace` persists `TestResultModel` rows referencing `model` while it's still Hibernate-transient, which throws `TransientPropertyValueException` on flush. Fix is to move the `if (isNewJob) jobRepository.persist(model)` above the `ingestTrace` call. Also flagged but unfixed: `submission.receivedAt` can be null for a new submission (aggregate's `receivedAt` is nullable, only conditionally set) causing an NPE in `ingestTrace`'s `.isAfter()` check; and `testResult.failMessage` gets set to `""` instead of `null` for passing tests.
- `V2__GroupMemberUniqueConstraint.sql` no longer exists — user merged it into `V1__Init.sql` directly, since nothing on this branch has been deployed to staging/prod yet. Same approach used for all schema changes today (discovered_test table, test_result FK swap, new unique indexes) — everything lives in `V1__Init.sql`, no `V2__`/`V3__` files added.

**Still open / not yet decided:** the `DiscoveredTest` staleness/picker-filtering question from 2026-08-25 (never revisited).

**2026-09-10/11 session — grade computation business logic, `GradingService`:**

- Start-of-session Flyway error (`relation "idx_group_member_definition_group_login" already exists`, migration `V2__GroupMemberUniqueConstraint.sql` reported as failing) was **not** a real migration problem: the file had been deleted from `src/main/resources/db/migration` (merged into `V1__Init.sql`, per the 2026-08-26 note above) but a stale compiled copy remained in `target/classes/db/migration` — `mvn`'s `resources:resources` copies but never deletes orphaned files no longer present in source. Fixed with `mvnw clean` (not `-Dmaven.build.cache.skipCache=true`, which is [[project_maven_build_cache_gotcha]]'s **different** fix for a **different** root cause — that one is the build-cache extension not restoring `target/classes` at all after a `pom.xml` edit; this one is plain stale leftovers after deleting a source file. Different symptoms: build-cache issue shows up as install/packaging errors right after a `pom.xml` edit; this one shows up as an old file's *content* still being used at runtime after deleting it). Follow-on: IntelliJ then showed a bogus "`;` expected" error on a valid for-each loop — caused by its indices being stale relative to the post-`clean` state, fixed with Maven reimport / Invalidate Caches, not a real code issue.
- Wrote `GradingService.computeGradeReport` / `computeGradingNode` (recursive, non-leaf aggregation) / `computeLeafResult` (leaf resolution chain: `NodeReference.TestCaseRef` → `SubmissionDefinitionModel` → student's `groupSlug` (`GroupMemberRepository.groupSlugForLogin`) → picked `SubmissionModel` (`SubmissionRepository.getPickedSubmission`, since changed to return `Optional`) → current `JobModel` (new `JobRepository.findCurrentBySubmission`, added this session) → `DiscoveredTestModel` (`findByKey`) → `TestResultModel`). Real bugs found and fixed along the way: `SubmissionDefinitionRepository.findByUri` was package-private (called from a different package) — made `public`; `NodeResult.nodeId` was `UUID.randomUUID()` instead of the owning `GradingNodeModel.id` — fixed to reuse `node.id`, consistent with `nodeResults` being keyed by it.
- **Found the design doc** (see "How to apply" below) partway through — it had actually already been pointed to by this very memory's own "How to apply" line before this session started, but wasn't checked until the user gave the exact path; a `find`/`grep -r` search from `apps/srvc-grades` and repo-wide missed it because `LocalDocs/` at the repo root is a **symlink** to an external directory and neither tool follows symlinks into a directory by default (need `find -L`). See [[reference_localdocs_symlink]]. Reading it surfaced several real deviations between it and code written earlier this session, corrected mid-session:
  - `validationThreshold` must be normalized (`score/effectiveMax >= threshold`, fraction 0.0–1.0), not a raw score comparison — code had `score >= threshold` directly. Discussed whether teachers might prefer entering raw points instead; landed on keeping storage normalized (consistent with `effectiveMax` being deliberately never stored, per the doc, to avoid drift when siblings change) and pushing raw-points entry to the frontend as a UI-only conversion. Reasoning given, no explicit final "yes" from the user — confirm before implementing.
  - Mandatory-fail was assumed (by the assistant, incorrectly) to only flip `validated=false` while keeping the summed score — the doc's literal step 7 says to zero the whole node's score. Extensive discussion (see next bullet) superseded this entirely.
  - `NodeReference.TestCaseRef` should hold a direct `discoveredTestId: UUID` FK per the doc, not the `(submissionDefUri, classname, testName)` composite key the code currently uses to do a runtime `findByKey` lookup — **user confirmed, agreed to change this.**
- **Major mandatory-flag rework, not yet implemented.** Working through whether a mandatory child failing should zero just its own contribution to the parent's sum vs. the doc's literal "zero the whole parent's score" (both preserve the failing child's own `NodeResult` for stats either way — a parent never rewrites a child's map entry, so that concern doesn't actually distinguish the two options) led the user to conclude the entire per-parent-propagation mechanism might be a mix-up of two different features they'd been imagining. Landed on: `mandatory` should instead be a **global** invalidation flag — any node anywhere in the tree marked `mandatory`, if not `validated` per its own local threshold, invalidates the whole report/exam via a flat post-pass after normal recursive computation (e.g. `root` `NodeResult.withValidated(false)`), completely decoupled from normal score aggregation (`validated` stays purely local/informational, never affects what a parent sums). **User explicitly confirmed this direction** ("I think I will go towards the mandatory flag being a global invalidation flag") but is taking the weekend to think it over before implementing. Open sub-question, not yet answered: should a global mandatory failure also zero `finalGrade`, or just set `validated=false` and leave the honestly-computed number? Assistant recommended the latter (keep the number, flag invalid) since the ambiguity that made zeroing attractive in the nested-tree version goes away once it's a single global check.
- The design doc itself (`LocalDocs/grading-system-data-model-design-decisions.md`) still describes the old per-parent-propagation mandatory semantics (steps 7-8) — needs updating once the global-flag rework is finalized and implemented, so it stays the actual source of truth.
- **Not independently re-verified by the assistant:** user said they'd fixed the ignored-node handling (consolidate to one check, produce a real `IGNORED` `NodeResult` instead of a bare `continue`), the absence-behavior branch (score/effectiveMax/validated should actually vary by `PASS`/`FAIL`/`IGNORE`, not be hardcoded), and the leaf `validated`-via-`testResult.success` question — but the assistant did not re-read the file after those fixes were reported. Also unresolved from this session: the root-node iteration bug in `computeGradeReport` (was looping over `gradingScheme.nodes`, which is *every* node in the scheme flat, not just roots — `scheme_id` is `NOT NULL` on all rows, `parent_id` is nullable) is superseded by the next point rather than fixed in place.
